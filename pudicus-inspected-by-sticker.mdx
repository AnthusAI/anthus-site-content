As AI coding swarms learn to build whole products overnight, the bottleneck shifts. The problem is no longer generating code; it is the leftover gates. QA, privacy, and security cannot stay on a human-critical path at agent speed. 

Consider SOC 2 compliance. For years, the industry standard for change management (CC8.1) relied on a simple proxy: a human reviewed every diff. But as Steve Yegge recently <Citation source="Yegge, yegge.ai Thunderdome, 2026">noted</Citation>, the traditional "Looks Good To Me" approval process is on life support. When fleets of agents merge code while you sleep, *review* can no longer mean one human approving every diff.

We need a change-management receipt designed for agents. That is why today we are open-sourcing **Pudicus** (modest, chaste, keeping pure): a standalone, pluggable inspection gate for Git commits.

## The Agricultural Inspector’s Produce Sticker

Pudicus was built to shift left the problem of secrets and confidential information leaking into source code. In the era of agentic coding, a specific problem arises: **How do we ensure that autonomous AI agents (or hurried humans) actually run the necessary security checks before committing code?**

Pudicus acts like an agricultural inspector's produce sticker. It intercepts commits at the staging area and runs a suite of deterministic scanners—like `gitleaks` to find AWS keys, or our own Tactus agent to prevent confidential client names from being mentioned in the source code.

If the tree is clean, Pudicus generates a cryptographically verifiable receipt proving the code was scanned, and appends it to the commit message:

```text
Inspected-by: pudicus-v1
Inspection-tree: f18588e0c5f5b0a5ba281b5a78242127919d2388
Inspection-result: clean
Inspection-at: 2026-08-31T17:01:34Z
Inspection-sig: hmac-sha256:8cce6e3714782d025eb4ec4aec755...
```

A downstream deploy gate in your CI/CD pipeline then prevents the truck from unloading if the stickers are missing. 

## Give an Agent a Tool

Pudicus is not a Sigstore fortress or a pentest-grade lock. It is a process safeguard. It solves the process hole of an agent (or human) bypassing validation (`--no-verify`) or deploying without looking. 

Because the agent does not have access to the cryptographic secret required to mint the signature, the absolute easiest path for an agent to get its code deployed is to simply let the hook run the scanners. It is a classic case of <Citation source="Anthus, Give an Agent a Tool">Give an agent a tool and nobody has to fish</Citation>. The agent will use the tool rather than attempt to forge a hash.

## Retroactive Approval and Signature Pooling

Git commit hashes change if you modify a commit message, which makes adding signatures to old commits painful. Pudicus solves this by tying the signature to the **Tree Hash** (the actual codebase state) rather than the commit hash.

If an agent bypasses the hook, or if you are onboarding an older project, you can run `pudicus approve`. This creates an empty "paperwork" commit at the tip of your branch that holds the pooled signatures for the older, unsigned trees. It provides a clean escape hatch that achieves full compliance without rewriting Git history.

## The New Form of Evidence

SOC 2 CC8.1 is a process criterion, not an authorship rule. It states that an entity must authorize, design, develop, test, approve, and implement changes. By pairing a deterministic validator (like Pudicus) with a fail-closed deploy gate, organizations can provide a traceable, checkable path from request to deploy—without demanding a human read every diff an agent writes.

Pudicus gives your agents the tools to prove they did the work safely.
